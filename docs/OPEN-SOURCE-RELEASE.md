# Thor Capture 开源发布执行清单

更新：2026-09-26。主计划与任务状态统一在 [ROADMAP.md](ROADMAP.md)，本文件只细化 P7 的交付材料和发布顺序。清单未勾选即尚未验收；这是计划，不代表已经获得许可、完成 CI 或发布。

## 1. 发布方案

建议第一个公开版本为 **0.1.0-beta.1**，以 Windows 绿色包和源码形式发布。先完成核心流程与稳定性，后续 0.2.x 扩展截图管理/导出，1.0 在公开测试及长期回归后发布。

首发包建议只包含 Thor Capture 自有程序和文档，不捆绑 ADB/FFmpeg。保留现有依赖查找机制，加首次引导和路径检测：缺 ADB 仍可浏览图库；缺 FFmpeg 可截图/兼容预览，禁用流解码和合成并说明。依赖来源与版本需要记录，不能让用户误以为开箱具备所有能力。

公开代码许可证建议 MIT，**尚未选定**。版权主体、代码来源、品牌使用、第三方文件需要先查清，再由权利人确认。现有代码可以继续内部开发，不应先给不确定的素材加公开许可。

## 2. 归属、素材和依赖清单：P7-1 / P7-2

逐项建立来源表，至少记录：文件/包、用途、来源URL或原项目commit、作者/权利人、版本、SHA-256、许可、改动、是否捆绑、需附带的通知和源码获取方式。不能只写「来自互联网」。

| 对象 | 当前处理建议 | 公开前检查 |
|---|---|---|
| 自有 C# / PowerShell / 文档 | 拟采用统一开源许可 | 移入代码的原许可、贡献归属、版权主体 |
| 自绘外壳、AYN/Thor 名称和刻字 | 开发版保持现有用户要求 | 非官方关系、商标/标识边界；自绘不自动取得商标许可 |
| 用户实拍参考照片 | 默认不随源码/包分发 | 如要公开，确认使用许可并去除EXIF/私人画面 |
| 官网产品照片 | 默认只留来源链接、不分发 | 不能因官网公开可看就当可再分发 |
| 游戏截图、录像、输入轨迹 | 默认全部排除 | 示例采用合成测试画面，公开真实样例需明确许可和隐私检查 |
| ADB / Platform-Tools | 首发用户自行配置 | 实际组件及包许可；官方SDK条款与独立开源组件许可分清 |
| FFmpeg | 首发用户自行配置 | 实际buildconf、GPL/LGPL组合、对应源码与通知；不是只看名称 |
| 将来可选scrcpy等后端 | 未选定，不进入首发包 | 设备端组件、分发许可、版本兼容、安装/清理行为 |
| 图标、字体或新图片 | 优先自绘/系统已有资源 | 下载素材的许可和字体是否真的随包分发 |

FFmpeg 的分发条件取决于实际构建；GPL 组件会改变 FFmpeg 包的许可条件，含不可再分发配置的包不能作为普通公开发行物。调用外部程序与再分发该二进制是两件事；自有代码许可与捆绑包义务分别审查。[FFmpeg 法律说明](https://ffmpeg.org/legal.html)。

ADB 要核实际组件许可，不能把整个 SDK 的下载授权直接当二进制再分发授权。[Android SDK 条款](https://developer.android.com/studio/terms)、[Platform-Tools 官方入口](https://developer.android.com/tools/releases/platform-tools)。MIT 的选择依据权属确认，并保留要求的版权/许可通知。[MIT 官方文本](https://opensource.org/license/mit)。

- [ ] 来源表与代码来源核查完成，权利人确认自有许可/版权主体。
- [ ] LICENSE、THIRD-PARTY-NOTICES 与实际代码/包一致。
- [ ] 确认是否捆绑；若捆绑，完成所需通知、对应源码提供与实际版本核对。
- [ ] 公开演示图、图标、README媒体均有可说明的来源和授权。
- [ ] 未解决的许可/权属问题从公开内容移除或阻止发布。

## 3. 公开内容审查：P7-3

审查三个范围：当前工作树、准备公开的 Git 历史、最终压缩包。`.gitignore` 只防止今后误加入，不能清除已有历史。

- [ ] 查设备serial、无线地址/配对码、token/密钥、私人账号邮箱和本地用户名路径。
- [ ] 查截图/MP4/GIF/照片EXIF、输入CSV、包名清单、配置、诊断和失败恢复路径。
- [ ] 排除 artifacts、evidence、backups、logs、用户图库、输入映射与个人配置。
- [ ] 把公开测试夹具换成可重建的合成图/视频与假设备数据，不依赖真实机器文件。
- [ ] README和帮助只用通用路径；私有备份路径留在本地交接资料，不在公开说明中。
- [ ] 日志/诊断功能说明记录内容、保留位置/周期、如何删除，默认不上传。
- [ ] 公开历史若需重写，先备份私有原仓库；再评估原仓库清理还是干净仓库首发，保留来源/贡献记录。
- [ ] 使用发布allowlist后仍检查最终ZIP内每个文件，不能直接打包整个工作目录。

## 5. CI和构建证明：P7-5

PR默认运行离线编译与相关测试，主分支运行完整离线回归/合成流/渲染/包审查，tag准备发布候选。硬件测试独立记录，不能让CI报告设备已通过。

- [ ] Windows runner存在可用Framework编译器，源码发现/程序集路径不依赖私人盘符。
- [ ] FFmpeg集成的来源/版本/许可/哈希固定，获取失败不能悄悄当通过。
- [ ] UI/STA测试与离屏渲染能在runner上实际运行；不能运行的项明确报告并另行验收。
- [ ] 进程/管道测试有超时，失败时保留脱敏结果而非挂住runner。
- [ ] Actions固定完整commit SHA，默认最小只读权限；不信任外部PR代码，不给它发布秘密。
- [ ] 发布job单独限制写权限、保护tag/环境，在候选审阅后手动触发。
- [ ] manifest含commit/tag、dirty标记、编译器/系统/依赖版本、构建命令、各文件哈希。
- [ ] 确认一次clean clone构建，并用故意失败的测试验证CI真实非零退出。

安全配置依据 [GitHub Actions 官方实践](https://docs.github.com/en/actions/reference/security/secure-use)。构建可追溯与二进制逐位可复现分开；后者需控制环境并重复比对，未完成不写入宣传。

## 6. 发布包与干净机器验收：P7-6

建议命名 `ThorCapture-0.1.0-beta.1-windows.zip`；仅发布确认支持的架构，不因当前AnyCPU就标已支持全部架构。包内容目标：

```text
ThorCapture.exe
LICENSE
THIRD-PARTY-NOTICES.md
QUICKSTART.zh-CN.md
QUICKSTART.en.md
release-manifest.json
```

ZIP外同时提供 `SHA256SUMS.txt`、Release Notes和对应源码tag。若最终方案增加文件，逐项更新allowlist；不含路径配置/旧EXE/候选测试程序。运行时自行创建用户配置和日志，EXE所在目录不可写时有可用数据目录。

- [ ] 核定最低系统、运行时和架构；建议首测Win11/.NET4.8，不能把Framework编译器路径当支持声明。[运行时依赖](https://learn.microsoft.com/en-us/dotnet/framework/install/versions-and-dependencies)。
- [ ] 干净标准用户解压、首次启动、无设备/无依赖、配置路径、保存截图和回看可按文档完成。
- [ ] 路径含中文/空格、只读EXE目录、DPI矩阵、第二实例、旧配置升级与回退通过。
- [ ] 已声明硬件能力绑定当前EXE哈希实测；双屏拒绝/输入无权限/FFmpeg缺失正确降级。
- [ ] 整段视频完整解码、停止/取消/断线原片恢复通过；不以MP4顶层结构替代解码。
- [ ] 包内容与源码/版本一致，计算ZIP和EXE校验和，无任何用户数据。
- [ ] 明确实际签名状态；评估证书成本与维护，不承诺未签名包没有系统安全提示。
- [ ] 发布候选冻结后改代码即重建/重测受影响项/更新哈希；旧报告不得套新包。

## 7. 公开发布顺序：P7-7

1. 开发与修复：完成ROADMAP的R2门槛，列出剩余限制与实验开关。
2. 内容冻结：生成候选、哈希、源码版本、兼容表、许可清单、Release Notes、干净包验证记录。
3. 最终审阅：用户确认仓库/公开内容/许可证与允许发布；此前准备工作可自主继续。
4. 公开动作：只在确认后推送公开内容、创建tag与Release，上传对应ZIP/校验和。
5. 发布后检查：从真实Release下载核对哈希、链接/文档版本与资产；本地候选不能替代真实交付。
6. 缺陷处理：标严重问题/撤下有风险的包，保留恢复说明与上一可用版本；公开历史和他人下载不能当作完全可撤销。

Release Notes模板至少包括：本版解决的问题、实际功能、设备/系统支持、实验或不可用能力、依赖配置、升级/回退、测试边界、已知限制。若输入或双屏未验收，明确关闭/实验，不将「实现已有」写成「实机通过」。

## 8. 发布后维护：P7-8

- [ ] 版本/数据schema分开编号，变更日志注明兼容变化，升级备份可还原。
- [ ] 数据丢失/误杀其他进程/泄漏私密资料为最高优先级；不能仅靠说明降级严重缺陷。
- [ ] 新固件/连接/系统纳入支持矩阵前补实际证据，未知不称兼容。
- [ ] 实验转稳定要验收；长期不可靠的声音/长录屏/后端明确延期。
- [ ] PR审查核对必要测试、原片保护、线程资源和许可；不强求每个低风险文档改动重跑全部实机。
- [ ] 至少一次公开测试/反馈修复与紧急回退演练，再按ROADMAP门槛进入1.0。

不在本计划内承诺自动更新器、代码签名采购、付费服务或固定维护SLA；确有需要再定义独立任务。
