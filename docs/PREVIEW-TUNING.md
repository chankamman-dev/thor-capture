# 预览参数与延迟（2026-09-27）

入口：主窗口第二行「预览设置」。应用时停止旧管道，等拥有的编码/解码任务清理后按新参数恢复；不改截图、录屏或已有素材。无需连接设备即可保存参数。

## 可调参数

| 项目 | 范围/行为 |
| --- | --- |
| 预览屏幕 | 双屏、仅上屏、仅下屏；单屏不启动另一块屏的编码器 |
| 视频高度上限 | 0–2160；0 为原生。按原比例缩放，宽度也限制为高度上限的16:9，编码尺寸取偶数；不放大小屏 |
| 每屏码率 | 0.1–100 Mbps；真实传给设备的 `--bit-rate`，双屏是两路各自的预算 |
| 电脑显示帧率上限 | 1–120 fps；限制最新帧交给预览区的频率，不限制设备编码，也不保证绘制能达到该值 |
| 取景方式 | H.264 持续视频流；或原生 PNG 连续截图。PNG 不经视频压缩，不縮小源像素，但获取很慢 |

五个预设：低延迟360p/2Mbps、均衡540p/3Mbps、清晰720p/8Mbps、原生20Mbps、原生PNG。预设是调参起点，不是设备测得的性能承诺。保留旧默认：540p/3Mbps、双屏。修改字段后标为自定义。

`artifacts/thor-capture-settings.txt` 新键：`previewHeight`、`previewBitRate`、`previewFps`、`previewScreens`（0双屏/1上屏/2下屏）、`previewPixels`（1为PNG）。异常数值恢复默认，其余外壳、灯光、保存目录设置保留。

## 如何调

先选择低延迟档、显示上限60；需要更清晰时逐档提高尺寸和码率。只需要一块屏时改为单屏，减少编码与电脑解码工作。原生高画质档增加工作量，不能保证同时降低延迟；降低显示上限可减轻电脑绘制负担，但不会减少设备编码负担。PNG 用于检查原生像素，不用于追求高帧率游戏预览。

H.264 为有损编码，原生尺寸/20Mbps也不能称为无损。现有 [Android screenrecord 源码](https://android.googlesource.com/platform/frameworks/av/+/refs/heads/main/cmds/screenrecord/screenrecord.cpp) 使用显示刷新率配置编码器，命令行没有源端帧率控制。因此界面没有把电脑限帧冒充源端控制。设备厂商的编码器行为尚未重新验证。

## 管道变更

- ADB→解码器使用4KB块写入并及时Flush，避免小包留在主机写缓冲。
- FFmpeg保留单线程、low_delay、小探测预算；增加fpsprobesize=0、pipe blocksize=4096、rawvideo flush_packets=1，及时写出完整帧尾。
- 不使用可能丢弃探测关键帧的nobuffer，不随意丢H.264包；只有解码后的完整旧帧被替换。每路最多一个待显示位图，不排队播放历史画面。
- 显示限帧使用绝对节拍、跳过错过的时隙。15ms UI时钟下60fps不会因每次重置截止时间而落到约33fps。按键动画保持独立时钟、3D部件及局部失效。
- 兼容取景保留快速原始像素优先、未知格式回退PNG，并遵守屏幕选择与尺寸上限；主动原生PNG不依赖FFmpeg。切换设置拒绝旧generation，等待尚在进行的截图，不和新的编码器重叠启动。

## 数值的含义与验证

界面显示每屏真实解码接收fps、交给预览区的送显fps；送显不是实际完成绘制的fps。静态场景可能不产生新帧，显示0不等于断线。未测量设备画面产生时刻，不能显示“实时延迟Xms”。代码的QueueAge只表示最新位图在电脑邮箱中等待的时间。

本批次179项离线检查（132项基础与47项视频流/播放器检查）通过，证据 `evidence/preview-regression.txt`。新增18项基础、8项流检查覆盖原生/偶数尺寸、坏设置、真实参数、源fps边界、限帧节拍、PNG像素、下屏单图、配置快照、单帧替换、运行时切换和清理。合成输入的首帧/接收/送显/替换数及邮箱年龄记录于 `evidence/thor-capture-tests/preview-host-metrics.txt`，不是Thor延迟测试。

界面与四配色离线检查：`evidence/ui-check/preview-settings.png`、`window.png`、`window-playback.png`。按照用户本轮选择，不运行ADB实机检查。USB端到端延迟、不同档位实际FPS/画质、180秒续流和长时间资源仍待设备验收；P3-3保持待实机状态。

若这些参数仍不能达到目标，P3-6需要验证可选的专用低延迟采集后端，源端帧率/编码器配置和带时间戳传输都要在该阶段实现，不在当前screenrecord管道上添加无效参数。
